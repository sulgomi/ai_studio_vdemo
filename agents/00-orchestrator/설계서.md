# 00 E2E 오케스트레이터 (코드, LLM 없음)

## 1. 역할

단계 순서를 정하고, 각 에이전트를 공통 봉투로 부르고, 검증기와 게이트를 돌리고, 반려 시 허용된 경로로 되돌리고, 사람 확인 지점에서 멈췄다가 이어 가고, 모든 것을 기록한다. 내용은 만들지 않는다.

하지 않는 일: 에이전트 대신 판단하기, 상한 없이 재시도하기, 사람 확인 없이 컨셉 확정·영상 렌더.

## 오케스트레이터가 둘인 이유

전체 흐름(00)은 단계 순서, 게이트, 되돌림 상한이 고정이라 **코드**가 맡는다. 시장조사 총괄(01)은 질문마다 다음에 누구를 더 부를지가 달라져 **LLM(Sonnet)이 그 안쪽 흐름만** 정한다. 01은 00의 한 단계(research) 안에서만 동작하고, 00은 01 안쪽 판단에 끼어들지 않는다.

## 2. 위치

E2E 모드(③)의 최상위. 개별 에이전트 모드(①)에서는 "앞 단계 자동 선행"과 기록 조회만 쓴다. 시장조사 모드(②)에서는 부르지 않는다(시장조사 총괄이 직접 대화).

## 3. 상태(RunState)

| 키 | 내용 |
|---|---|
| `run_id`, `today`, `request` | 실행 id, 기준일, 요청문 |
| `scope` | intake 결과: target_segment, card_type, target_adopt(기본 0.38), constraints, assumptions |
| `outputs` | 에이전트 id → 최신 출력 봉투(버전 목록은 Ledger) |
| `cells_top` | 기회 점수 상위 12셀 |
| `chosen_pick` | H2에서 고른 셀 |
| `eval` | 컨셉 안별 지표 |
| `winner` | card, metrics, ranking |
| `counters` | 회귀 합계, 에이전트별 재시도, 컨셉 재작업 수 |
| `human` | H1~H5 상태(pending, decided, skipped)와 결정 내용 |
| `trace` | 이벤트 목록 |

노드는 멱등이다. 노드 단위로 체크포인트를 남겨 중간에서 재개한다(A ref/agent_core, D 결정 08).

## 4. 처리 흐름

| 순서 | 노드 | 하는 일 | 다음 |
|---|---|---|---|
| 1 | `intake` | 규칙으로 타깃·카드 유형·숫자 목표를 뽑고, 못 뽑은 것만 경량 모델로 해석(D chat: 규칙 먼저, LLM은 애매할 때만). 해석 결과는 가정으로 기록 | `h1_scope` |
| 2 | `h1_scope` | 사람 확인(interrupt). 답이 없으면 30분 뒤 기본 해석으로 | `research` |
| 3 | `research` | research_lead 호출(workflow 모드). 시장조사 총괄이 trend·competitor·consumer를 부르고 종합 | `score_cells` |
| 4 | `score_cells` | 세그먼트 팩과 시장조사 결과로 세그먼트×니즈 기회 점수 계산(니즈 가중치 × 공백도 × 트렌드 강도), 상위 12셀 | `whitespace` |
| 5 | `whitespace` | whitespace 호출 | `feasibility_gate` |
| 6 | `feasibility_gate` | 셀마다 채택 천장 계산, 목표 미만 셀 제거. 모두 제거되면 `h1_scope`로 | `h2_pick` |
| 7 | `h2_pick` | 사람이 셀 선택. 답이 없으면 1순위 | `concept` |
| 8 | `concept` | concept 호출(3안) | `eval_concepts` |
| 9 | `eval_concepts` | 안별 지표 계산(아래 5절), 통과 안 중 종합 점수 최고를 승자로. 통과 0건이면 사유 코드와 함께 `concept` 재작업 | `validation` |
| 10 | `validation` | 코드 시뮬레이션 후 페르소나 LLM 호출 | `adopt_gate` |
| 11 | `adopt_gate` | target_adopt ≥ 목표, adopter_profit ≥ 1.5. 미달이면 최다 거절 사유를 넣어 `concept` 재작업(최대 2회), 그래도 미달이면 `whitespace` 다음 셀 | `guardrail` |
| 12 | `guardrail` | guardrail 호출. fix가 있으면 수정안으로 `concept` 재작업 1회 후 `eval_concepts`부터 다시 | `h3_legal` |
| 13 | `h3_legal` | needs_human 항목을 담당 부서에 배정(대기하지 않고 표시만) | `h4_confirm` |
| 14 | `h4_confirm` | 사람이 컨셉 확정. 재작업 요청이면 사유를 넣어 `concept` | `design_marketing` |
| 15 | `design_marketing` | 전략 → 보드 생성. needs_research가 있으면 trend를 evidence_pack 모드로 부르고(기록 우선) 1회 갱신 | `h5_render` |
| 16 | `h5_render` | 스토리보드 미리보기 확인 후 렌더 승인 여부(승인 없으면 렌더하지 않음) | `plan_doc` |
| 17 | `plan_doc` | plan_doc 호출 → 수치 대조 검증. 보강 요청이 있으면 승인된 것만 해당 파트 자문 1라운드 후 재작성 | `finalize` |
| 18 | `finalize` | 산출물 묶음(JSON, 기획서 md, 보드·영상 링크, trace) 저장 | 끝 |

## 5. 컨셉 평가(코드) 출력 `eval`

안마다 다음을 계산한다(A `h.js evalConcept`). 수치 모형은 PM 가정치다.

| 필드 | 뜻 | 통과 기준 |
|---|---|---|
| `profit` | 정적 손익(만원/인/년) | ≥ 3 |
| `novelty` | 공백 태그 비중 기반 새로움 0~1 | 참고 |
| `sim`, `nearest` | 최근접 경쟁 카드 유사도와 카드명(태그 + 혜택 유형군) | ≤ 0.5 |
| `cx`, `indepCx`, `appliedCx` | 자기보고 복잡도, 규칙 수 기반 추정, 적용값(차이가 크면 평균) | appliedCx ≤ 0.5 |
| `adopt`, `adopterProfit`, `cherry` | 빠른 시뮬레이션의 타깃 채택 의향, 채택 고객 손익, 체리피커 비중 | adopt ≥ 0.38, adopterProfit ≥ 1.5 |
| `special_point_ok` | 특별한 포인트 유효(흔한 표현만이면 무효, 기존 카드 설명과 같으면 무효, D originality) | true |
| `errs` | 금칙어, 미등록 태그, 혜택률 범위(0 초과 0.03 이하) 위반 | 0건 |
| `pass` | 위 모두 충족 | |

`winner` = { card: 승자 안 원문, metrics: 승자 지표, ranking: [{i, name, score, pass}] }. 종합 점수는 profit, novelty, (1−sim), (1−appliedCx), adopt의 가중 합(가중치는 설정값, 기본 균등).

## 6. 하네스(모든 호출 공통)

1. 예산 확인(호출 수, 토큰, 시간)
2. 입력 검증: payload를 해당 `in.schema.json`으로
3. LLM 호출(구조화 출력, 단일 강제 도구 호출 방식)
4. 출력 검증: 봉투 스키마 → result 스키마 → 출처 대조 → 금칙어·준법 → 에이전트별 검증기
5. 반려면 `_common/rework.prompt.md`로 1회 재요청. 두 번째 반려는 사람 확인 큐로
6. 기록: 이벤트, 토큰, 시간, 모델, 캐시 여부

## 7. 상한(설정값)

| 항목 | 기본 |

## 8. 사람 확인 지점

H1~H5(01 문서 5절). interrupt가 있는 노드는 재개 시 처음부터 다시 실행되므로 interrupt 앞에 LLM 호출이나 부작용을 두지 않는다(D CLAUDE.md 주의 사항).

## 9. 모델

없음. intake의 해석 보조만 경량 모델(Haiku)을 쓴다(03 문서).

## 10. 평가

- 시나리오 10개(타깃 7종 + 모호 요청 3종)로 E2E 완주율, 회귀 횟수, 상한 도달률, 사람 대기 시간 측정
- 같은 입력 3회 실행의 승자 일치율(실행 간 변동 측정, A 실험 5절의 교훈)

## 11. 출처

A `agents/orchestrator/README.md`, `live/h.js`(evalc, winner, pack2), 허브 구조도(하네스 6단계, 상한 8회), D `graphs/pipeline.py`·`interactive.py`(interrupt 3곳), D 결정 01·02·08·10, A AWS 구조도(Step Functions). 상태 키 이름과 H3·H5 지점은 새로 정함.

## 12. 한계

- 기회 점수와 시뮬레이션 수치는 가정 기반 모형이다. 고객 데이터로 보정하기 전에는 후보 간 순위로만 읽는다.
- 실행마다 컨셉 결과가 달라진다(A 실험에서 확정 카드가 실행마다 바뀜). 데모는 저장본 재사용 모드(C의 데모 모드)로 고정한다.
