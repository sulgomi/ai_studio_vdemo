# 03 경쟁사 (competitor)

## 1. 역할

시판 카드의 혜택 구조를 같은 양식으로 정리하고, 혼잡 영역(많은 카드가 쓰는 혜택 태그), 공백 영역(거의 안 쓰는 태그), 타깃과 가장 가까운 경쟁 카드 3종, 따라 하기 쉬운 영역을 낸다. 자사 카드는 사용자가 이름을 말했을 때만 조회해 같은 양식으로 나란히 비교한다. 자사 카드사가 설정된 환경(own_issuer)에서는 그 카드사 카드(is_own)를 경쟁 집계(혼잡·공백·최근접 경쟁 카드)에서 빼고, 자사 비교 칸(comparison_with_own_card)에 차이점·공백을 먼저 쓴다.

하지 않는 일: 비공개 수익성·가입자 수 단정, 소비자 반응 분석, 규제 해석.

## 2. 위치

- 단독 대화 가능(①). 시장조사 총괄이 부름(②, ③).
- 다운스트림: whitespace(crowded, empty, nearest), concept(empty, crowded, products 벤치마크), 코드 평가(경쟁 DB로 유사도 계산), plan_doc.

## 3. 입력

봉투 + payload: allowed_tags, competitor_db(카드별 태그·기준일), own_issuer, target_segment, card_names(사용자가 말한 카드), depth.

## 4. 처리 흐름

| 단계 | 종류 | 내용 |
|---|---|---|
| plan | LLM | 영역 밖 여부, 되물을 것(자사 카드명이 불분명할 때만), 조회할 카드 목록 |
| 코드 확인 | 코드 | 자사 카드는 사용자가 말한 이름일 때만. 카드명 전처리(정규화 → 별칭표 → 자모 유사도 0.85 → 경량 LLM 선택 → 그대로) |
| lookup | 코드 | depth=overview면 주제로 시장 검색해 후보 카드만, detail이면 card_info_lookup(DB→공시→웹, 부족분만 하위 소스, 충돌 보존, 7일 저장본) |
| 집계 | 코드 | competitor_db 태그 집계(카드 수), 상위 8개 태그 계산 |
| answer | LLM | 조회 결과와 집계만 근거로 crowded, empty, nearest, easy_to_copy, 비교 |
| check | 코드 | 태그 ∈ allowed_tags, nearest 이름 ∈ DB, products는 조회 결과에서 코드가 옮김, 확인 불가·충돌은 limits에 |

## 5. 출력

`result`: crowded[], empty[], nearest[], easy_to_copy[], products[], comparison_with_own_card, db_as_of.

## 6. 요건

| ID | 요건 | 검사 |
|---|---|---|
| CP-R1 | crowded, empty의 tag는 allowed_tags 안에서만 | 코드 |
| CP-R2 | nearest 카드명은 competitor_db 또는 조회 결과에 있는 카드 | 코드 |
| CP-R3 | empty로 적은 태그를 실제로 8개 넘는 카드가 쓰면 반려 | 코드 집계 |
| CP-R4 | crowded는 DB 집계 상위 8개 태그와 겹쳐야 함(겹치지 않는 태그는 이유 필수) | 코드 |
| CP-R5 | 모든 상품 정보에 확인 일자, 프로모션 종료일 | 스키마(products는 코드가 옮김) |
| CP-R6 | 혜택은 같은 양식(항목, 할인·적립률, 월 한도, 전월실적, 연회비) | 스키마 |
| CP-R7 | 자사 비교는 유사점보다 차이점·공백을 먼저 | 지시 |
| CP-R8 | 확인되지 않은 수치는 "확인 불가" | 코드: 출처 없는 숫자 제거 |

## 7. 검증기와 반려

ENUM_UNKNOWN(CP-R1), ID_UNKNOWN(CP-R2), GATE_FAILED(CP-R3), 경고(CP-R4), DB 기준일(`db_as_of`)이 없으면 경고.

## 8. 게이트·회수

없음. 시장기회 단계가 반려 사유로 "근거 공백"을 내면 depth=detail로 1회 재호출.

## 9. 도구

card_info_lookup, web_search(공시 도메인 제한 검색 포함).

## 10. 모델

답 작성 기본 Haiku, 올릴 때 Sonnet(depth=detail 비교, 충돌 3건 이상, 자사 비교). 카드 정보 추출은 Haiku. 근거: A 실험(DB 태그 집계)에서 세 모델 4.25~4.5로 차이가 작았다. 실제 웹 조회·추출은 C에서 기본 Opus, 추출만 Haiku로 돌았으므로 W1 재비교 대상이다.

## 11. 평가

C `evals/competitor_scenarios.json`(되묻기, 영역 밖, 조회 여부, 비교표), `evals/gold_card_facts.json`(카드 정보 정답 후보, 사람 확인 후 사용), A의 empty 태그 오판 검사.

## 12. 출처

A `agents/02-comp`(계약·검증기), C `agents/competitor/`, `tools/card_lookup/`(DB→공시→웹, names.py), C design.md 6-1·6-6. tags 부호화 필드와 db_as_of는 새로 정함.

## 13. 한계

- 경쟁 카드 DB 34종에 기준일이 없다(A). 고객 카드 DB 연동 전까지 공시 재확인 필요.
- 숫자 확인은 표기가 다르면('1만5천원' 대 '15,000원') 맞는 값도 비운다(C).
- 카드사 공시 페이지가 JS로 그려지면 본문이 비어 외부 검색으로 넘어갈 수 있다(C).
