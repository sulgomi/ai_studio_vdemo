# 04 소비자 (consumer)

## 1. 역할

타깃 세그먼트의 니즈 우선순위, 채택 장벽, 꼭 있어야 하는 것과 포기할 수 있는 것을 정리한다. 공개 웹·커뮤니티 자료가 있으면 선택 동기, 불만, 이탈 사유, 반응 경향을 더한다.

하지 않는 일: 자사 회원·결제 데이터 조회, 개인 식별 정보 처리, 카드 스펙 확인(경쟁사 영역), 반응 비율을 실제 이용 비중처럼 말하기.

## 2. 위치

- 단독 대화 가능(①). 시장조사 총괄이 부름(②, ③). trend 결과가 필요하므로 E2E에서는 trend 다음 또는 trend 결과가 오면 후속 호출.
- 다운스트림: whitespace(top_needs, must_have, can_give_up, evidence_signal_ids), concept(같은 필드), plan_doc.

## 3. 입력

봉투 + payload: segment(세그먼트 팩: 월 소비, 복잡도 허용도, 니즈 가중치, 모두 PM 가정치), need_labels, trend_signals(id, title, impl), public_sources_enabled.

## 4. 처리 흐름

| 단계 | 종류 | 내용 |
|---|---|---|
| plan | LLM | 영역 밖 여부, 되물을 것, 검색어(공개 웹 사용 시) |
| search | 코드 | 공개 웹(web_search). 감성 데이터·커뮤니티 API는 연동 전 stub("미연동") |
| answer | LLM | 니즈 우선순위와 장벽, 반응 경향 |
| check | 코드 | need 키 ∈ need_labels, signal id 실재, 표본 수(근거 문서 수) 계산, 5건 미만이면 비율을 쓰지 않고 신뢰도 하향, 이메일·전화번호 모양은 [가림], "언급·반응 경향이며 실제 이용 비중이 아님" 문구와 편향 경고 부착 |

## 5. 출력

`result`: top_needs, must_have, can_give_up, barriers, evidence_signal_ids, sentiment(공개 웹이 있을 때), themes, purchase_drivers, churn_reasons, bias_warning.

## 6. 요건

| ID | 요건 | 검사 |
|---|---|---|
| CS-R1 | top_needs의 need는 need_labels 키 | 코드 |
| CS-R2 | evidence_signal_ids는 입력 시그널 id | 코드 |
| CS-R3 | top_needs마다 근거(evidence)에 세그먼트 수치 또는 시그널 id를 적음 | 스키마 + 지시 |
| CS-R4 | 반응 비율은 표본 5건 이상일 때만, "언급 경향" 표기 | 코드 |
| CS-R5 | 사용량(많이 쓰는 곳)과 선택 동기(고르는 이유)를 구분 | 심사 |
| CS-R6 | 개인 식별 정보 미포함 | 코드 마스킹 |
| CS-R7 | 포기 가능한 것은 니즈 점수를 근거로 | 지시 |

## 7. 검증기와 반려

ENUM_UNKNOWN(CS-R1), ID_UNKNOWN(CS-R2), 경고(CS-R4 위반은 코드가 비율 삭제).

## 8. 게이트·회수

없음.

## 9. 도구

web_search(공개 웹). sentiment, community는 연동 시 같은 자리에 붙임(C `agents/consumer/sources.py`의 fetch만 채움).

## 10. 모델

기본 Haiku, 올릴 때 Sonnet(공개 웹 근거가 10건 이상이거나 충돌이 있을 때). 근거: A 실험 Opus 4.5, Haiku 4.0, Sonnet 3.25로 표본 변동 범위 안. 발행일 누락은 모델이 아니라 필수 필드 검증기로 막는다.

## 11. 평가

C `evals/consumer_scenarios.json`, A의 need 키·근거 id 검사.

## 12. 출처

A `agents/03-cons`(계약), C `agents/consumer/`(공개 웹, 표본·편향·마스킹 규칙), C design.md 6-7. A·C 필드 통합은 새로 정함.

## 13. 한계

- 세그먼트 수치는 PM 가정치다. 고객 집계 통계로 교체하는 것이 가장 큰 개선점이다(PM 문서 데이터 요청).
- 커뮤니티 의견은 혜택 민감층에 치우친다. bias_warning을 항상 붙인다.
