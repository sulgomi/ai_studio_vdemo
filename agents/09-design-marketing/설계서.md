# 09 디자인·마케팅 (design_marketing)

## 1. 역할

확정된 카드 브리프를 받아 ① 마케팅 방향성 전략 → ② 디자인 보드 7장(컨셉 보드 1, 시안 목업 3, 디자인 포인트 3) → ③ 영상 스토리보드 3종(릴스 9:16 15~20초, 유튜브 16:9 25초, 홍보 16:9 20초)을 만든다. 최종 상품명 후보 3개와 추천 1개도 여기서 정한다. 사람이 확정하면 그때만 영상 MP4를 렌더한다.

원칙: LLM은 JSON만 만들고, 생김새는 템플릿(보드 렌더러, 스토리보드 플레이어, 캠페인 보고서)이 책임진다.

하지 않는 일: HTML·CSS·코드 작성, 혜택·수치 지어내기, 실존 브랜드·카드 네트워크·발급사·유명인 연상, 승인 전 영상 렌더.

## 2. 위치

- S7. 업스트림: concept(winner.card), validation(twin 요약, voices), guardrail(pass가 아닌 항목, required_disclosures), trend(시그널과 출처).
- 다운스트림: H5(렌더 확정), plan_doc(3-1 디자인 컨셉, 5 마케팅 전략, 6 홍보 영상 콘셉트 보드), 사용자 뷰(캠페인 보고서).
- 단독 대화 가능(①): 고객이 한두 문장 브리프만 주면 E 원래 동작 그대로.

## 3. 입력

봉투 + payload: brief(파이프라인이 만든 브리프), guard_open_items, required_disclosures, twin_facts, voices_summary, trend_signals, research_pack, existing_card_names, banned_words, launch_date, formats.

브리프 변환 규칙(코드):

| E 브리프 항목 | 파이프라인에서 채우는 값 |
|---|---|
| 타깃 | winner.card.cvp.target, scope.target_segment |
| 일상 맥락 3~5개 | concept.cvp + consumer.purchase_drivers에서 코드가 뽑지 않고, LLM이 브리프에서 추론(assumed 표시) |
| 무드 | concept.special_point.hook, consumer must_have에서 LLM이 추론 |
| 카드 종류 | scope.card_type (debit은 E 스키마의 check로) |
| 혜택 목록 | winner.card.mechanics와 rates에서 코드가 headline·condition으로 변환한 것만(E 규칙: 받은 것만 쓴다) |
| 금지 표현 | 02 문서 5절 금칙어 + guardrail suggestion에서 금지된 문구 |

## 4. 처리 흐름(E 도구 루프)

| 순서 | 도구 | 검수(코드) | 비고 |
|---|---|---|---|
| 1 | `create_strategy` | qa.check_strategy + 금융 규칙 | 페르소나 3명이 시안 3개 코드를 미리 정함 |
| 2 | `create_card_boards` | qa.check_boards(팔레트 대비 4.5:1, 시안 차별화, 글자 수, 금지어, 숫자) + 이름 유사도 + 금융 규칙 | 혜택이 있으면 needs_compliance_review=true |
| 3 | `create_storyboard` ×3 | qa.check_storyboard(장면 길이 합 = duration_s, 자막 6단어, 안전 영역) | 렌더 없이 실시간 미리보기 |
| 4 | (needs_research가 있으면) 오케스트레이터가 trend evidence_pack 호출 후 `update_strategy` 1회 | | 주제 3개 이하 |
| 5 | H5 승인 후 `render_video` | approval_quote 필수 | 승인 없으면 렌더 안 함 |

검수 실패 시 실패 항목을 돌려보내 1회 재생성, 다시 실패하면 사람에게(E 설계서).

## 5. 출력

`result`(out.schema.json): naming, strategy(E 스키마), boards(E 스키마), storyboards(reels, youtube, promo, 각 E 스키마), segment_plays, compliance, needs_research, render_jobs.

다음이 읽는 필드: plan_doc ← naming, strategy, boards(concept, variants의 code·name·story), storyboards(scenes 요약), segment_plays, compliance, needs_research.

## 6. 요건

E 원문 규칙(kit/system_prompt.en.md, 한국어판 system_prompt.md)에 아래 금융·파이프라인 요건을 더한다.

| ID | 요건 | 검사 |
|---|---|---|
| DM-R1 | 이름 후보 3개 + 추천 1개, 추천 ∈ 후보, boards.brand.name = 추천 | 코드 |
| DM-R2 | 이름이 existing_card_names와 글자쌍 유사도 0.5 이상이면 반려, 0.3 이상이면 경고 | 코드 |
| DM-R3 | 이름·태그라인·카피에 금칙어·수익 암시 없음 | 코드 |
| DM-R4 | 혜택은 brief.benefits에 있는 것만, 숫자 변경·반올림·상향 금지 | qa.py + 코드 |
| DM-R5 | 혜택이 있으면 needs_compliance_review=true, 스토리보드 legal_footer | qa.py |
| DM-R6 | 투자 연계면 legal_footer와 strategy.risks에 원금 손실 고지 | 코드 |
| DM-R7 | 가드레일 fix·needs_human 항목은 strategy.risks에 반영(항목 id 인용) | 코드 |
| DM-R8 | 체리피커·휴면 위험형 대응을 segment_plays에(twin 비중·손익은 입력 값 그대로) | 스키마 + 코드 |
| DM-R9 | 채널 선택 근거가 입력에 없으면 needs_research에 주제를 쓰고 추측하지 않음 | 지시 + 심사 |
| DM-R10 | KPI 목표는 [목표값], 런칭 단계는 D-day 상대 일수 | qa.py |
| DM-R11 | 경쟁사 이름·비교 금지(포지셔닝) | qa.py 금지어 |
| DM-R12 | render_video는 H5 승인 문구가 있을 때만 | 코드 |

## 7. 검증기와 반려

E qa.py의 오류 문자열은 반려 코드로 바꿔 전달한다: 스키마 → SCHEMA_INVALID, 금지어 → BANNED_WORD, 지어낸 숫자 → NUMBER_NOT_IN_INPUT, 대비·글자 수·장면 길이 → COUNT_OUT_OF_RANGE, 이름 → NAME_TOO_SIMILAR, 고지 → MISSING_DISCLOSURE.

## 8. 게이트·회수

- 기록 우선 재조사: needs_research → trend(evidence_pack) 1회.
- H5: 스토리보드 미리보기 확인 후 렌더 승인.
- 수정 요청은 처음부터 다시 만들지 않고 update_* 부분 패치(E).

## 9. 도구

E `kit/tools.json`의 7개: create_strategy, update_strategy, create_card_boards, update_card_boards, create_storyboard, update_storyboard, render_video. 이 에이전트는 결과를 도구 입력으로만 낸다(Bedrock Converse toolConfig).

## 10. 모델

Opus. 근거: A 실험 브랜딩 Opus 4.8, Sonnet 4.0, Haiku 3.6(채널 수 지시 위반, 합산 혜택 오인 카피), 마케팅 Opus 4.8, Haiku 4.6, Sonnet 4.0(일정 계산 오류). 비용을 줄일 때 update_* 패치만 Sonnet으로 내릴 수 있다.

## 11. 평가

- E `tests/`: 에이전트 루프(가짜 Bedrock), 렌더러, 플레이어, 자막 대비 전 프레임 검사(visual_check.py)
- 다른 브리프 3~5개 회귀(시안 차별화, 글자 수)
- 금융 규칙: 투자 연계 카드에서 고지 누락 0건, 혜택 숫자 변경 0건
