# 01 시장조사 총괄 (research_lead)

## 1. 역할

시장 질문을 트렌드·경쟁사·소비자 관점으로 나눠 세 에이전트를 병렬로 부르고, 결과가 올 때마다 후속 조사를 정하고, 근거별 종합·충돌·불확실을 정리한다.

하지 않는 일: 직접 사실을 지어내기, Agent 결과끼리 충돌할 때 하나로 합치기, 근거 없는 결론.

## 2. 위치

- 시장조사 모드(②)의 대화 상대. 여러 턴 대화, 주제는 사용자가 "새로운 주제"라고 할 때만 끊는다(C P-10).
- E2E 모드(③)의 S1 단계(workflow 모드). 결과는 시장기회·기획서가 쓴다.
- 단독 대화에서 넘어온 요약(`conversation.summary`)이 있으면 다시 묻지 않고 이어 간다.

## 3. 입력

봉투 + `payload`(in.schema.json): scope, prior_turn_findings(앞 턴 근거), handoff_from(단독 대화 인계), report_requested, limits.

## 4. 처리 흐름

| 단계 | 종류 | 내용 |
|---|---|---|
| plan | LLM | new_topic 여부, 되물을 것(꼭 필요할 때만 1개), 세 에이전트에 보낼 질문(각 영역 관점으로 다듬은 한 문장), depth, 맥락 갱신 |
| 확인 | 코드 | 있는 에이전트만, 중복 없이, 자사 카드명은 사용자가 말한 것만 |
| research | 코드 + LLM | 새 주제면 세 에이전트를 동시에 넓게(경쟁사는 overview). 결과가 하나 올 때마다 plan LLM이 다음 호출 0~2개 또는 "충분"을 정함. 같은 에이전트는 한 번에 하나, 같은 질문 반복 금지, 상한(호출 7, 판단 5, 240초) |
| 되물음 처리 | 코드 | 에이전트가 범위를 되물으면 "전체 대상으로"라고 답하고 다시 부름. 자사 카드명 되물음만 사용자에게 |
| synthesize | LLM | 한 줄 결론, 핵심 발견, 기회·위험, 제언, 영역별 근거, 충돌(나란히, 가정별), 불확실, 다음 질문 |
| 확인 | 코드 | 근거 줄과 핵심 발견은 실제 finding id를 가리켜야 남김. 출처는 그 finding에서 코드가 옮김. 결론 숫자 대조 |
| verify | 경량 LLM + 코드 | 결론·근거 문장마다 받침/부분/근거 없음/반대 판정, 집계·합격은 코드. 결과는 limits에 `[답 검증]` 줄로(본문은 고치지 않음, C P-5 B안) |

리포트 요청(`report_requested=true`)이면 에이전트를 새로 부르지 않고 대화 전체 근거로 문서형 보고서를 만든다.

## 5. 출력

`result`: headline, answer_body, key_findings, evidence, opportunities, risks, recommendations, conflicts, uncertainties, calls, agent_outputs, verification, report_markdown.

다음 단계가 읽는 필드: whitespace ← headline, key_findings, conflicts(→ 긴장 단서). plan_doc ← headline, key_findings, conflicts, uncertainties.

## 6. 요건(지시문·검증기 공통 원본)

| ID | 요건 | 검사 |
|---|---|---|
| RL-R1 | 새 주제는 세 에이전트 모두 호출 | 코드: calls round 1에 3개 |
| RL-R2 | 근거 줄·핵심 발견은 finding id 1개 이상 | 코드: id ∈ 받은 findings |
| RL-R3 | 충돌은 합치지 않고 positions 2개 이상으로 | 스키마 |
| RL-R4 | 결론 문장의 수치는 근거 finding에 있는 값 | 코드: 수치 대조 |
| RL-R5 | 종합 순서: 결론 → 근거(영역별) → 충돌 → 불확실 → 다음 질문 | 스키마 순서 + 화면 |
| RL-R6 | 상한 준수(호출 7, 판단 5) | 코드 |
| RL-R7 | 답 검증 "근거 없음·반대" 비율이 20% 초과면 경고 | 코드(임계값 임의 초안) |

## 7. 검증기와 반려

SCHEMA_INVALID, ID_UNKNOWN(없는 finding id), NUMBER_NOT_IN_INPUT(결론 수치), COUNT_OUT_OF_RANGE(새 주제인데 호출 3 미만). 반려는 synthesize만 다시 한다(에이전트 재호출 없음).

## 8. 게이트·회수

- 한 에이전트가 실패해도 나머지로 종합하고 실패를 limits에 남긴다.
- 기획서의 보강 요청이 오면 해당 영역 에이전트를 1~2회만 다시 부르는 "자문" 모드로 동작한다(D backup consult).

## 9. 도구

직접 쓰는 도구 없음. 세 에이전트 호출 함수(call_agent)만.

## 10. 모델

plan Sonnet, synthesize Sonnet, verify Haiku. 복잡한 충돌이 3건 이상이면 synthesize를 Opus로(03 문서).

## 11. 평가

C `evals/orchestrator_scenarios.json` 유형(되묻기, 영역 밖, 단독→통합 인계, 의식의 흐름, 리포트, 한글 카드명) 20~30턴. 지표: 호출 정확도(필요한 에이전트를 불렀나), 되묻기 적절성, 충돌 보존, 답 검증 받침 비율, 반복 3회 안정성.

## 12. 출처

C `agents/orchestrator/prompts.py`, `schemas/orchestrator.py`, `verify_answer.py`, docs/proposals.md P-5~P-10, design.md 6-4. A 허브의 서브 오케스트레이터(호출 상한, 범위 확장 사유 기록). workflow 모드와 whitespace 연결 필드는 새로 정함.

## 13. 한계

- 답 검증도 LLM이라 사람이 표본을 확인해야 한다.
- 결과가 오는 순서에 따라 후속 조사가 달라질 수 있다. 데모 모드는 보낸 순서대로 판단해 고정한다(C 커밋 a39e153).
