# 리포트 템플릿 규칙 (시장조사 4종)

원칙은 디자인·마케팅 레포와 같다. **LLM은 칸을 채우는 JSON만 만들고, 긴 보고서의 모양은 템플릿(UI)이 책임진다.**
에이전트가 보고서 문장을 처음부터 길게 쓰지 않는다. 모양은 템플릿, 내용은 칸, 숫자·출처는 코드가 옮긴다.

## 공통

- 단독 대화에서 "리포트로 보여줘"를 요청하거나 총괄이 종합할 때 UI가 아래 템플릿으로 렌더한다.
- 칸마다 길이 상한(문장 수 또는 글자 수)과 형식을 둔다. 상한을 넘으면 검증기가 반려한다(`LEN_OVER`).
- 칸에 들어가는 숫자는 출처가 있는 값만 허용한다. 출처 없는 숫자는 코드가 제거하고 "확인 불가"로 표시한다.
- 칸을 못 채우면 비워 두지 않고 `unresolved`에 사유를 적는다.
- 칸을 채우는 일은 정해진 형식이라 기본 모델은 Haiku다. 근거가 많거나 충돌이 있을 때만 Sonnet으로 올린다(03_모델_추천.md).

## 경쟁사 리포트 (`result` 필드 → 섹션)

| 순서 | 섹션 | 채우는 필드 | 칸 규칙 |
|---|---|---|---|
| 1 | 한 줄 결론 | `answer` | 1~2문장, 600자 이내 |
| 2 | 혼잡한 영역 | `crowded[]` | 항목당 tag + reason 1문장, 건수는 코드 |
| 3 | 빈 영역 | `empty[]` | 항목당 tag + reason 1문장, 건수는 코드 |
| 4 | 가장 가까운 카드 | `nearest[]` (최대 5) | name + why 1문장, 카드는 DB와 대조 |
| 5 | 따라 하기 쉬운 것 | `easy_to_copy[]` | 항목당 1문장 |
| 6 | 상품 비교표 | `products[]` | 코드가 조회 결과에서 옮김(LLM 작성 금지), 확인 일자 필수 |
| 7 | 자사 비교 | `comparison_with_own_card` | 차이점·공백 먼저, 유사점은 뒤 |
| 8 | 근거·한계 | `sources`, `unresolved`, `db_as_of` | 코드 |

## 소비자 리포트

| 순서 | 섹션 | 칸 규칙 |
|---|---|---|
| 1 | 한 줄 결론 | `answer` 1~2문장 |
| 2 | 니즈 우선순위 | 순위 + 이유 1문장, 근거 finding id 필수 |
| 3 | 선택 동기 | 항목당 1문장 + 언급 경향(많음/보통/적음), 실제 비율로 단정 금지 |
| 4 | 장벽·불만 | 항목당 1문장 + 근거 |
| 5 | 근거·한계 | 코드(출처, 발행일, 충돌) |

## 트렌드 리포트

| 순서 | 섹션 | 칸 규칙 |
|---|---|---|
| 1 | 한 줄 결론 | `answer` 1~2문장 |
| 2 | 시장·결제 시그널 | 시그널 + 강도 + 출처 |
| 3 | 규제 | 항목 + 시행일 + 출처 |
| 4 | 신기술 | 항목 + 카드 적용 가능성 1문장 |
| 5 | 근거·한계 | 코드(18개월 초과 출처 경고) |

## 시장조사 총괄 리포트

섹션은 `headline`, `answer_body`(3~5문장), `key_findings`, `opportunities`, `risks`, `recommendations`, 영역별 근거, `conflicts`(나란히, 가정별), `uncertainties`, 다음 질문 순서로 고정한다. 자유 서술 보고서는 만들지 않는다. 충돌은 하나로 합치지 않고 나란히 보여 준다.

## 화면 규칙

- 사용자 뷰는 위 순서대로 섹션 카드를 그린다. 데이터가 없는 섹션은 "정보 없음 + 사유"를 보여 준다.
- 개발 뷰는 같은 JSON을 칸 단위로 펼치고, 칸별 검증 결과(길이, 출처, 코드 채움 여부)를 표시한다.
