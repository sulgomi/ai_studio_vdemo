# 10 기획서 (plan_doc)

## 1. 역할

모든 단계의 JSON을 모아 고객이 준 7개 섹션 틀의 카드상품 기획서(마크다운)를 쓴다. 수치는 입력에 있는 값만 인용하고, 고객 데이터가 필요한 항목은 비워 두지 않고 무엇이 필요한지와 지금의 대체 근거를 쓴다. 근거가 부족하면 앞 파트에 보강을 요청할 수 있다(1라운드).

하지 않는 일: 새 수치 추정, 입력에 없는 URL 인용, 내부 필드명 노출, BEP를 개월 수로 단정.

## 2. 위치

S8. 업스트림: 전 단계. 다운스트림: 사용자 뷰 보고서 패널(마크다운→HTML), 내보내기(md, 이후 DOCX).

## 3. 입력(받는 필드를 열거, 통째 적재 금지)

| payload 키 | 출처 필드 |
|---|---|
| research | research_lead.result의 headline, key_findings, conflicts, uncertainties + trend.result.signals(id, title, impl, reliability) + competitor.result(crowded, empty, nearest) + consumer.result(top_needs, must_have, can_give_up) |
| opportunity | whitespace.result.picks + chosen_pick |
| final_card | winner.card(라벨 치환본: 필드명 대신 한국어 라벨) |
| final_metrics | winner.metrics |
| alternatives | 탈락 안: working_title, 탈락 사유, 지표 |
| twin, voices | validation.result.twin, voices |
| guardrail | guardrail.result 전체 |
| design_marketing | naming, strategy(positioning, pillars, channels, phases, kpis, risks), boards(concept, variants의 code·name·story 요약), storyboards(형식별 장면 요약), segment_plays, compliance, needs_research |
| template | 고객 틀(7섹션 제목과 소제목) |
| style | 문체 규칙 |
| needs_client_data | 고객 데이터 필요 목록 |
| rr_teams | R&R 부서 5곳 |
| schedule_note | 일정 가안 |
| allowed_urls | 코드: 전 단계 sources의 URL 합집합 |
| allowed_numbers | 코드: 입력에 나온 수치 목록(퍼센트 표기 포함) |
| decision_log | 코드: trace에서 뽑은 회수·결정 이력 요약 |

## 4. 처리 흐름

| 단계 | 종류 | 내용 |
|---|---|---|
| draft | LLM | 7섹션 + 부록 |
| check | 코드 | 아래 요건 검사 |
| review | 경량 LLM | 가장 아픈 반론 1개, 보강 요청 0~3건(part, section, question) |
| approve | 코드 | 보강 요청 승인: 구현된 파트만, 사내 자료 요청 거절, 중복 거절, 1라운드 |
| consult | 해당 파트 | 검색 1~2회 + 메모(D backup consult) |
| revise | LLM | 메모를 반영해 해당 섹션만 재작성. 앞 결정과 충돌하면 앞 단계를 다시 돌리지 않고 리스크에 "[보강 확인]"으로 |
| finalize | 코드 | 미검증 항목(가상 시뮬레이션, 가드레일 needs_human, 고객 데이터 필요)을 항상 부록에 붙임 |

## 5. 출력

`result`: markdown, sources_used, unverified_items, backup_requests, section_index, title, tagline.

## 6. 요건(지시문·검증기 공통 원본, A 실험 4절의 반려 원인을 지시문에 포함)

| ID | 요건 | 검사 |
|---|---|---|
| PD-R1 | 섹션 제목 정확히: "## 1. 요약", "## 2. 시장 조사와 기획 배경", "## 3. 신상품 컨셉과 가치 제안", "## 4. 재무 타당성과 사업 효과", "## 5. 마케팅 전략 방향", "## 6. 홍보 영상 콘셉트 보드", "## 7. 추진 일정과 부서별 R&R", "## 부록" 순서대로 | 코드 |
| PD-R2 | 맨 앞에 보고서 이름, 카드 가칭(추천 이름), 한 줄 카피 | 코드 |
| PD-R3 | 채택 의향은 퍼센트 소수 첫째 자리(예: 39.6%), 정적 손익·채택 고객 손익은 입력 값 그대로 | 코드 |
| PD-R4 | 입력에 없는 퍼센트·수치 0건 | 코드(allowed_numbers 대조) |
| PD-R5 | 섹션 4에 "포트폴리오"와 "BEP"라는 단어로 자사 포트폴리오 영향과 손익분기를 다루고, 고객사 데이터 필요를 표시. BEP를 개월 수로 단정하지 않음 | 코드 |
| PD-R6 | R&R 부서 5곳 모두 언급 | 코드 |
| PD-R7 | 입력에 없는 URL 0건(allowed_urls) | 코드 |
| PD-R8 | 리스크 언급(가드레일 needs_human 전부 부록에) | 코드 |
| PD-R9 | 시뮬레이션 수치 인용 문장 주변에 "가상 고객 시뮬레이션(가정 기반)" | 코드 |
| PD-R10 | 내부 필드명(segId, capPerCat, no_cap, minPerf, cx 등) 노출 0건 | 코드 |
| PD-R11 | 문체: 줄표, "~가 아니라 ~다", 굵은 라벨 불릿, 홍보 어휘, 한 줄 마무리 문장 금지 | 코드(경고 3건 이상이면 반려) |
| PD-R12 | 부록: 에이전트 협업·결정 이력, 대안 후보와 탈락 사유, 가드레일 needs_human 전체, 근거가 약한 항목, 출처 링크 | 코드 |
| PD-R13 | 고객 데이터가 필요한 항목은 무엇이 필요한지와 대체 근거를 씀(빈칸 금지) | 심사 |

## 7. 검증기와 반려

SECTION_MISSING(R1, R2, R12), NUMBER_FORMAT(R3), NUMBER_NOT_IN_INPUT(R4), MISSING_DISCLOSURE(R5, R9), COUNT_OUT_OF_RANGE(R6), SOURCE_URL_UNKNOWN(R7), STYLE_VIOLATION(R10, R11).

## 8. 게이트·회수

검증 반려 1회 재작업(사유 코드). 보강 요청 1라운드 3건. 그래도 남으면 사람에게(개발 뷰 경고).

## 9. 도구

없음(보강은 오케스트레이터가 해당 파트를 consult 모드로 부름).

## 10. 모델

기본 Sonnet, 올릴 때 Opus. 근거: A 실험 세 모델 모두 첫 시도 반려(지시문에 요건 누락이 원인), 점수 Haiku 4.6, Sonnet 4.4, Opus 4.2. Haiku는 토큰 214k·359초로 가장 무거웠고, Opus는 순위 오류와 문체 위반이 있었다. review는 Haiku.

## 11. 평가

- 같은 입력에서 첫 시도 통과율(요건이 지시문에 들어간 뒤 목표 80% 이상)
- 수치 대조 위반 0건, 필드명 노출 0건
- 상품개발부 기획서 검수(형식·현업 활용성)

## 12. 출처

A `agents/10-doc`(7섹션 틀, 검증기 V.doc2, 문체 검사 aitell), A `docs/함께쌓기카드_기획서.md`(완성 예시), D `agents/product_plan`(미검증 항목, 검토자, 보강 요청 루프), D 결정 17·27. 입력 열거와 allowed_numbers·allowed_urls는 새로 정함.
