# 에이전트 설계서(고객 검토용) 작성 템플릿

## 이 템플릿의 용도

고객사가 개발 중인 에이전트를 이해하고 피드백을 주면, 그 피드백으로 개발 방향을 1차 확정한다. 개발자용 설계서(`agents/<폴더>/설계서.md`)는 스키마, 검증 코드, 반려 코드까지 다루고, 고객 검토용 설계서는 그중 고객이 판단할 수 있는 부분만 업무 언어로 옮긴다.

고객이 결정할 수 있는 지점이 문서에 보여야 한다. "이렇게 만들었습니다"로 끝나면 피드백이 "좋네요"나 "잘 모르겠어요"에서 멈춘다. 항목마다 우리 기본안과 다른 선택지를 같이 적어서 고객이 고를 수 있게 한다.

## 작성 원칙

1. 독자는 카드 상품기획 실무자와 의사결정자다. 개발 용어(스키마, 봉투, 토큰, interrupt)는 쓰지 않거나 처음 한 번 풀어 쓴다.
2. 내부 필드명(segId, capPerCat, no_cap 등)은 쓰지 않는다. 화면과 기획서에 나오는 한국어 이름을 쓴다.
3. 숫자는 출처를 붙인다. 리허설 값이면 "리허설 기준", PM 가정치면 "가정치"라고 적는다.
4. 시뮬레이션 수치를 예측이나 전환율처럼 쓰지 않는다. "가상 고객 시뮬레이션(가정 기반)"이라고 적는다.
5. 피드백 질문은 예/아니오로 끝나지 않게, 선택지와 우리 기본안을 같이 쓴다.
6. 한 에이전트는 A4 두세 장 안에서 끝낸다. 길어지면 부록으로 뺀다.
7. 문체: 줄표(—), "~가 아니라 ~다" 대비, 굵은 라벨 불릿, 홍보 어휘("혁신적", "강력한"), 한 줄짜리 마무리 문장을 쓰지 않는다.

## 문서 전체 구성

| 순서 | 장 | 내용 |
|---|---|---|
| 0 | 문서 정보 | 버전, 작성일, 검토 요청 기한, 피드백 받을 방법 |
| 1 | 전체 그림 | 서비스가 하는 일, 에이전트 구성도, 이용 방식 3가지, 사람 확인 지점 |
| 2 | 공통 원칙 | 모든 에이전트가 지키는 규칙(출처, 수치 계산, 사람 확인) |
| 3 | 에이전트별 설계 | 아래 "에이전트 1개당 항목"을 에이전트 수만큼 반복 |
| 4 | 피드백 요청 모음 | 3장의 피드백 질문을 한 표로 모은 것. 고객은 이 표만 채워도 된다 |
| 5 | 용어 | 처음 보는 사람이 막힐 단어 |

## 에이전트 1개당 항목과 작성 가이드

각 항목마다 무엇을 쓰는지, 작성 팁, 예시를 적었다. 예시는 경쟁사 에이전트 기준이다.

### 1) 한 줄 정의

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 이 에이전트가 무슨 일을 해서 무엇을 내놓는지 한 문장 |
| 작성 팁 | 주어는 에이전트, 목적어는 산출물. "지원합니다", "도와줍니다" 대신 실제로 만드는 것을 쓴다 |
| 좋은 예 | 시판 카드 34종의 혜택을 같은 양식으로 정리하고, 붐비는 혜택과 비어 있는 혜택, 우리 타깃과 가장 가까운 카드 3종을 찾아낸다 |
| 나쁜 예 | 경쟁사 분석을 지원하는 AI 에이전트입니다 |

### 2) 현업에서 대신하는 일

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 지금 기획 담당자가 손으로 하는 어떤 일을 대신하거나 줄이는지. 대신하지 않는 일도 같이 |
| 작성 팁 | 현행 업무를 고객이 알아볼 수 있게 쓴다. 소요 시간 단축 같은 효과 수치는 측정 전이면 쓰지 않는다 |
| 좋은 예 | 카드고릴라·카드사 공시를 열어 혜택표를 엑셀로 옮기고 태그를 붙이던 일. 혜택 원가나 가입자 수 추정은 하지 않는다 |
| 고객이 줄 수 있는 피드백 | "우리는 이 일을 이렇게 하지 않는다", "이 일이 더 아프다" |

### 3) 언제 쓰나(이용 방식)

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 개별 에이전트 대화, 시장조사, E2E 상품기획 중 어디에서 동작하는지. 단독으로 부를 때와 다른 에이전트가 부를 때 차이 |
| 작성 팁 | 표 한 줄씩. 단독 대화가 가능하면 사용자가 실제로 칠 만한 질문 예시를 한 개 붙인다 |
| 예시 | 단독: "시판 카드 중 어디가 붐비고 어디가 비어 있어?" / 시장조사: 시장조사 총괄이 트렌드·소비자와 함께 부름 / E2E: 시장조사 단계 안에서 자동 실행 |

### 4) 받는 것(입력)

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 사용자가 주는 것, 앞 단계 에이전트에게서 받는 것, 외부 자료(웹, DB). 데모 단계에서 무엇이 가정치인지 |
| 작성 팁 | "고객사 데이터로 바꾸면 좋아지는 입력"을 따로 표시한다. 고객이 데이터 제공을 결정하는 근거가 된다 |
| 예시 | 타깃 세그먼트(사용자), 혜택 태그 목록(공통 설정), 경쟁 카드 DB 34종(공개 자료로 구축, 기준일 미기재). 고객사 카드 DB를 받으면 이 DB만 교체 |

### 5) 일하는 순서(처리 흐름)

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 3~6단계로 나눈 처리 순서. 단계마다 AI가 판단하는지, 코드가 계산하는지 표시 |
| 작성 팁 | "AI가 판단 / 코드가 계산 / 사람이 확인"을 같은 표기로 통일한다. 고객이 신뢰 수준을 가늠하는 핵심 정보다 |
| 예시 | ① AI: 조회할 카드 정함 → ② 코드: DB·공시·웹 순으로 조회 → ③ 코드: 태그별 카드 수 집계 → ④ AI: 혼잡·공백 해석 → ⑤ 코드: 없는 태그나 없는 카드명을 썼는지 검사 |

### 6) 내놓는 것(출력)과 예시

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 산출물 목록과 리허설 실제 출력 한 토막. 다음 단계가 이 결과를 어떻게 쓰는지 |
| 작성 팁 | 실제 출력 예시가 피드백을 가장 많이 끌어낸다. 샘플 파일(`samples/<폴더>/`) 경로를 같이 적는다 |
| 예시 | 비어 있는 혜택: 투자 리워드 0종, 포인트 주식 전환 0종(34종 기준, 리허설) |

### 7) 품질을 지키는 규칙

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 이 에이전트가 지켜야 하는 규칙 3~6개와 어기면 어떻게 되는지(자동 반려, 경고, 사람 확인) |
| 작성 팁 | 개발 설계서의 요건 표에서 고객이 이해할 수 있는 것만 고른다. 규칙 ID(CP-R1 등)는 괄호로 남겨 개발 문서와 연결한다 |
| 예시 | 비어 있다고 한 혜택을 실제로 8개 넘는 카드가 쓰고 있으면 자동 반려하고 다시 쓰게 한다(CP-R3) |

### 8) 사람이 확인하는 곳

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 이 에이전트 결과를 사람이 보고 결정하는 지점(H1~H5 중 해당하는 것). 없으면 "없음, 다음 단계 게이트에서 확인" |
| 작성 팁 | 답이 없을 때 시스템이 어떻게 하는지도 쓴다 |

### 9) 하지 않는 일과 한계

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 일부러 맡기지 않은 일, 현재 데이터·기술 때문에 생기는 한계 |
| 작성 팁 | 숨기지 않고 쓴다. 고객이 나중에 발견하면 신뢰가 깎이고, 먼저 말하면 데이터 제공이나 범위 결정의 근거가 된다 |
| 예시 | 경쟁 카드 DB에 기준일이 없다. 고객사 DB를 받기 전까지 공시로 재확인해야 한다 |

### 10) 이렇게 설계한 이유

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 핵심 설계 결정 1~3개와 이유. 버린 대안이 있으면 같이 |
| 작성 팁 | 리허설에서 실제로 생긴 일을 근거로 쓰면 설득력이 생긴다 |
| 예시 | 집계는 코드가 한다. AI가 혜택 태그 개수를 세면 실행마다 숫자가 달라졌기 때문이다 |

### 11) 고객 피드백 요청

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 고객이 결정하거나 의견을 줘야 방향이 정해지는 질문 2~4개 |
| 작성 팁 | 질문마다 "선택지 / 우리 기본안 / 답이 없으면"을 쓴다. 답이 없을 때 기본안으로 간다고 적어 두면 일정이 멈추지 않는다 |
| 형식 | 아래 표 |

| # | 질문 | 선택지 | 우리 기본안 | 답이 없으면 |
|---|---|---|---|---|
| CP-F1 | 자사 카드를 비교 대상에 넣을까요? | ① 사용자가 이름을 말한 카드만 ② 자사 전 상품 자동 비교 ③ 비교 안 함 | ① | ①로 진행 |

### 12) 데모에서 보이는 장면

| 구분 | 내용 |
|---|---|
| 무엇을 쓰나 | 데모 영상이나 시연에서 이 에이전트가 나오는 장면과 시간 |
| 작성 팁 | 스토리보드 장면 번호와 맞춘다. 고객이 영상을 보고 설계서로 돌아와 해당 에이전트를 찾을 수 있게 한다 |

## 검토 전 확인표

작성자가 배포 전에 확인한다.

- [ ] 에이전트마다 피드백 질문이 2개 이상이고, 질문마다 기본안이 있다
- [ ] "AI가 판단 / 코드가 계산 / 사람이 확인" 표기가 모든 처리 흐름에 있다
- [ ] 리허설 숫자에는 "리허설 기준", 가정치에는 "가정치"가 붙어 있다
- [ ] 내부 필드명과 개발 용어가 본문에 없다
- [ ] 4장 피드백 요청 모음 표가 3장의 질문과 개수·번호가 같다
- [ ] 개발 설계서와 규칙 ID가 연결되어 있다
- [ ] 문체 금지 항목(줄표, 굵은 라벨 불릿, 홍보 어휘)이 없다
